## CDP double-open probe

A second process was launched with `open -na`, a unique Chromium
`--user-data-dir`, and a CDP endpoint bound to `127.0.0.1`. The spawned
process used the temporary profile, and `lsof` confirmed that the selected
port listened only on loopback.

`/json/version` reported:

- Browser `Chrome/150.0.7871.128`
- CDP protocol `1.3`
- V8 `15.0.1240245`

`/json/list` exposed two visible `page` targets for `app://-/index.html`.
Neither had document focus. One was 408×400 with one `main`, no `nav`, and no
buttons; the other was 2560×1326 with two `main` elements, one `nav`, and 70
buttons. The larger target was therefore the main-shell candidate for this
probe.

This target shape establishes an important selection rule: do not attach to
the first `page`, and do not select only by URL, visibility, or focus. Filter
to the application URL, then compare expected shell structure and viewport
area. Revalidate the heuristic after every application update.

The probe intentionally read no conversation text, thread or project names,
PR titles, repository content, account details, tokens, private transport
data, or bundled source. It performed no product action and changed no
application setting.

project, execution environment, and worktree are separate state layers.

and generic `Projects` and `New Project` actions. No option names were

content, with the local creation action below the grouped rows. These
observations establish the container, grouping, scrolling, and control
lifecycle only; they do not reveal repository, project, worktree, thread,
account, or environment names.

The probe returned only allowlisted generic tokens and structural counts. It
did not read arbitrary visible text, submit a prompt, enter an existing task,
select a project, or invoke a repository action. The exact process was
terminated, port `9351` was confirmed closed, and its unique temporary profile

## Scoped synthetic thread-lifecycle probe

A later user-authorized capture used a new disposable task and a synthetic,
non-sensitive prompt: `Please reply with exactly: UI probe complete.` The
second process used loopback port `9361`, a unique temporary Chromium profile,
and the same structural target-selection rule. The main target was 2560×1410;
the separate 408×400 auxiliary page was excluded.

The current completed thread had a 46px header. Below it, the wide timeline
used a centered 768px outer column with 16px inline insets and a 736px content
column. Its first content began 32px below the header. The user turn was a
right-aligned rounded bubble; the assistant response remained flat and
left-aligned with a persistent four-action row.

The Composer used the same centered outer column. Its 736×98 card sat 16px
above the bottom edge. The editable region was 712×44. During submission, the
rightmost action became a 28×28 Stop control and the adjacent auxiliary control
was disabled. The synthetic reply reached its completed state after roughly
8.2 seconds. One live region was present throughout this sample; no
`aria-busy` element was exposed by the sampled current-build thread.

An 800×600 CDP device-metrics override was used only to inspect responsive
Renderer behavior; it was not treated as a native window resize. With the
274px sidebar still visible, the main region was 526px wide. The 46px header,
16px timeline/Composer insets, 494px Composer card, 98px card height, and 16px
bottom inset remained stable.

Only the synthetic prompt/reply, generic controls, allowlisted structural
facts, and representative measurements were inspected. Existing task,
project, repository, account, and sidebar text were excluded from the written
evidence. One accidentally broad temporary crop was deleted immediately and
replaced by a main-region-only crop before visual comparison.

This capture establishes the basic current-build thread composition and
submit/running/completed control transition. It does not establish every
Markdown shape, long-thread virtualization, real cancellation result,
reasoning, tools, approvals, panels, failures, or native window behavior.

## Main-only raster comparison

A follow-up capture on the same installed version disabled Renderer animation
and transition effects before measuring the viewport. The full 1346×820
Renderer screenshot was then cropped in memory from the stable 274px main
offset, producing a 1072×820 main-only reference. This avoided the coordinate
drift seen when a direct screenshot clip raced the application sidebar
transition. The raw application PNG remained outside the repository.

The independent demo exposes a deterministic
`?capture=current-thread` fixture with the same synthetic prompt and completed
reply. `scripts/check-current-thread-visual.mjs` renders that fixture in Chrome
at the reference dimensions and compares decoded PNG pixels. At a 0.05
pixelmatch threshold, the accepted sample differed by 3545 of 879040 pixels
(0.4033%). Its header, message band, and Composer region ratios were 2.4396%,
0.4861%, and 0.9551%. The shell geometry matched the observed state exactly:
46px header, 587×79 317×38 user bubble, 168×163 assistant column, 168×195
assistant actions, and 168×706 736×98 Composer.

This is a raster gate for one completed dark-theme thread state, not a
product-wide pixel-parity claim. Remaining differences are concentrated in
independently drawn icon paths and text rasterization. The package does not
redistribute the packaged OpenAI Sans font or application icon assets.

## Evidence scope

This update revalidates:

- the installed package metadata and fingerprint;
- loopback-only CDP availability through an explicitly launched second
  process;
- the current build's application-shell target shape and de-identified
  Projects-entry/list structure; and
- the current new-chat destination/context split, Project dialog shape, and
  Local environment dialog grouping and scrolling; and
- the current basic thread header/timeline/Composer geometry plus the
  submit/running/completed control transition in a disposable synthetic task;
  and
- the main-only completed-thread raster fixture and its regional diff gates.

It does not revalidate every state observed in `26.715.72359`. Those earlier
CDP records remain useful historical evidence tied to that build. Until a
surface is reached again on `26.721.41059`, it cannot satisfy the
current-build parity gate. Browser and Electron acceptance can still prove the
independent implementation is healthy, but cannot promote an old runtime
comparison to current-build verification.

The temporary Chromium profile isolates Chromium storage used by the spawned
process. It does not establish isolation of Codex account, task, project,
repository, or navigation state. A second process is therefore an observation
mechanism, not a safe second account or disposable Codex session.

CDP covers Renderer structure and behavior only. Native window composition,
system dialogs, app menus, title-bar behavior, real native resizing, and other
main-process surfaces still require manual or separate Electron-level
acceptance.
